# 模块台账建设与维护流程

> 本工作流是 [09-module-analysis.md](./09-module-analysis.md) 的**补强与延续**：
> - `09` 负责模块**首次分析**（回答"当前项目有哪些模块、每个模块是什么"）
> - `15`（本工作流）负责模块台账的**粒度规范、反向调用扫描、持续维护、时效性保证**（回答"台账怎么切、怎么保鲜、Agent 怎么用"）
>
> **最终目标**：让 Agent 在后续接到任何代码修改任务时，**先查台账定位相关模块**，快速理解模块能力边界与上下游影响面，从而"改得准、改得快、不漏改"。

---

## 概述

<!-- CONTENT_START: overview -->
本工作流规定了：

1. **模块粒度切分标准** — 什么样的代码集合算"一个模块"
2. **调用关系扫描规范** — 如何全面识别调用方（谁调我）与被调方（我调谁）
3. **台账自动维护机制** — 代码变更后如何让台账保鲜
4. **时效性校验规则** — Agent 使用台账前如何判断档案是否过期
5. **台账使用协议** — Agent 接到任务时，如何按顺序查台账、加载模块档案
<!-- CONTENT_END: overview -->

## 触发指令

### 用户手动触发

```
# 建立初次台账（如未建立）
建立模块台账
初始化模块台账

# 全量刷新
刷新模块台账
更新所有模块台账

# 局部刷新
更新 <模块名> 模块台账
刷新最近改动的模块台账

# 时效性检查
检查模块台账时效性
体检模块台账
```

### Agent 自动触发（强制）

以下场景 Agent **必须**自动执行台账维护，无需用户显式指令：

| 触发时机 | 应执行的动作 |
|---------|------------|
| 任何代码修改类任务**完成时** | 识别本次改动涉及的模块，调用「Step 5 · 增量更新」刷新对应模块档案 |
| 任何任务**开始时**读取 `modules/index.md` 后 | 对命中的模块执行「Step 6 · 时效性校验」，过期则先刷新再使用 |
| 新建/删除文件涉及模块边界变化时 | 识别是否需要新增/合并/拆分模块档案 |

> ⚠️ **硬性约束**：代码修改任务在向用户报告完成前，**必须**先完成受影响模块档案的更新，否则视为任务未完成。

## Step 1 · 模块粒度切分标准

> 核心原则：**以"逻辑功能是否闭合"为唯一硬标准**，行数/文件数仅作软性参考。

### 1.1 硬标准：逻辑功能闭合性（必须满足）

一个候选模块必须**同时**满足以下 4 条，才能作为独立模块建档：

| 判定项 | 通过条件 | 反例（不通过） |
|-------|---------|--------------|
| **职责单一** | 能用**一句话**描述该模块的核心职责，且不含"和/或"等并列词 | "处理用户登录**和**订单支付" → 应拆分 |
| **入口收敛** | 对外暴露的接口/API/函数集中在 1~2 个入口文件内 | 对外接口散落在 5 个以上文件 → 应拆分或重划边界 |
| **内聚闭合** | 修改该模块的功能**通常不需要**改动其他模块的内部逻辑（可以修改调用方，但不改被调方内部） | 改一个功能要跨改 3+ 模块的内部实现 → 边界划错了 |
| **数据自洽** | 模块拥有自己的核心数据结构，或仅使用被明确声明的共享数据结构 | 频繁读写多个陌生模块的私有数据 → 边界划错了 |

### 1.2 软标准：规模参考阈值（辅助判断）

以下阈值**只用于提示 Agent 复核**，不作为拆分/合并的强制依据：

| 规模指标 | 建议区间 | 越界处理 |
|---------|---------|---------|
| 单模块代码行数（不含空行/注释/自动生成） | 200 ~ 2000 行 | < 100 行 → 建议合并到相邻模块；> 3000 行 → 提示复核是否职责不单一 |
| 单模块文件数 | 3 ~ 20 个 | > 30 个 → 提示复核是否可拆分子模块 |
| 对外接口数 | 1 ~ 15 个 | > 25 个 → 提示复核是否职责过重 |

> ⚠️ 越界时**只提示、不强制**。如果 1.1 的 4 条硬标准全部满足，即使规模超标也保留为单模块（例如某些复杂领域的核心引擎）。

> 📌 **v1.10 补丁**：即使规模不越界，也要按 [1.6 递归下钻](#16-递归下钻硬标准v110-新增) 逐层验证候选模块目录内是否隐藏子模块；1.2 的越界只是**辅助信号**，不能作为"不越界=不用下钻"的免检凭证。

### 1.3 边界模糊时的裁决规则

遇到"这些代码到底算一个模块还是两个模块"的模糊情况，按下列优先级裁决：

1. **是否有独立入口** — 有独立 `index.*/main.*/mod.*` → 倾向独立模块
2. **是否被独立引用** — 外部代码只引其中一部分而不引另一部分 → 倾向拆分
3. **是否共享同一状态/数据** — 共享私有状态 → 倾向合并
4. **变更频率是否同步** — 历史 commit 显示总是一起改 → 倾向合并

> 记录裁决理由到目标模块档案的 `## 备注` 章节，便于后续复核。

### 1.6 递归下钻硬标准（v1.10 新增）

> 目的：解决 v1.9 的**扫描广度偏好** — Agent 面对目录树容易"扫一层就下结论"，把 `services/`（内含 order/user/payment 等 3+ 个 service）当成一个 services 模块。本节强制 Agent 对每个候选模块做**深度自证**，未证明目录内高内聚不允许直接建档。

#### 1.6.1 下钻硬性触发条件（满足任一即触发）

| 触发项 | 触发条件 | 下钻动作 |
|-------|---------|---------|
| **T1 · 目录深度** | 候选模块目录内**存在二级子目录**（不含 `test/tests/mock/mocks/generated/dist/build/vendor/node_modules/__pycache__` 等生成或测试目录） | 对每个二级子目录执行 1.6.2 的子域抽样验证 |
| **T2 · 文件规模** | 单模块文件数 > 30 或 代码行数 > 3000 | 强制拆分候选，按二级子目录初分，再各自跑 1.1 硬标准 |
| **T3 · 一句话职责含并列词** | 一句话职责含"和/或/、/以及/&/,"等并列词 | 视为**边界劣化**，强制回到 1.1 拆分或建 Group |
| **T4 · 入口分散** | 对外入口分布在 2+ 个二级子目录 | 检查这些子目录是否本就是独立模块 |
| **T5 · 档案膨胀** | 已建档模块的 `.md` 超过 800 行 或 内部主标题 ≥ 5 个 | 触发 1.6.3 反向审计，检查是否为伪单模块 |

#### 1.6.2 子域抽样验证流程（当 T1/T2/T4 触发时执行）

```
候选模块目录 M（含 N 个二级子目录 S1..SN）
   ↓
① 对每个 Si：
     a. 打开 Si 的入口文件（index.*/main.*/mod.* 或最大文件）
     b. 提取 Si 的核心导出符号 / 对外接口列表
     c. 用一句话概括 Si 的职责
   ↓
② 用 1.1 的 4 条硬标准验证「Si 能否合并进 M」：
     - 职责单一：M 的一句话职责能否覆盖 Si？
     - 入口收敛：Si 的入口文件是否也算 M 的对外入口？
     - 内聚闭合：修改 Si 内部功能是否会波及 M 的其他子目录？
     - 数据自洽：Si 是否共享 M 的核心数据结构？
   ↓
③ 判定：
     - 4 条全过 → Si 合并进 M（登记到 M 的「## 内部结构」章节，不单独建档）
     - 任一不过 → Si 独立成模块（走 Step 3 的 4~7 建档流程）
   ↓
④ 汇总所有 Si 的判定结果：
     - 独立子模块 ≥ 3 → 触发 1.4 建 Group（M 变 Group 目录，各 Si 变子模块）
     - 独立子模块 = 1~2 → M 保留为顶层，Si 各自成顶层单模块
     - 独立子模块 = 0 → M 确认为单模块，登记内部结构即可
```

**抽样最少数量约束**：

- N ≤ 5：**全部**二级子目录都要打开验证，不允许抽样
- 5 < N ≤ 15：至少验证 5 个，剩余可基于命名+文件规模启发式判断，但结论要写明依据
- N > 15：几乎肯定不是单模块，直接判为需要拆分/建 Group，不再走验证流程

#### 1.6.3 反向审计（当 T5 触发时执行）

针对**已建档但档案膨胀**的模块（`.md` > 800 行 或 主标题 ≥ 5 个），执行反向审计：

```
1. 读取该模块 .md 的所有二级/三级标题
   ↓
2. 提取其中"看起来像独立能力"的标题（如"XX 引擎 / XX 管理器 / XX 适配器 / XX 解析器"）
   ↓
3. 对每个候选能力，回到源码定位其对应的目录/文件集合
   ↓
4. 走 1.6.2 的验证流程判定是否需要拆分
   ↓
5. 若拆分：将该模块降级为 Group（单模块 → group.md），原能力拆为子模块
   ↓
6. 在原 .md 头部追加变更历史：`| YYYY-MM-DD | 反向审计拆分 | 由 T5 触发，拆出 X 个子模块 |`
```

#### 1.6.4 下钻审计记录格式（写入模块档案 `## 备注` 章节）

每次执行 1.6.2 或 1.6.3，都必须在目标模块档案末尾追加一段：

```markdown
## 备注 · 下钻审计记录

- **审计时间**：YYYY-MM-DD
- **触发条件**：T1（存在 3 个二级子目录）/ T3（一句话职责含"和"）/ ...
- **抽样范围**：N/M（抽样数/总子目录数）
- **判定结果**：
  | 子目录 | 一句话职责 | 独立性判定 | 处置 |
  |--------|-----------|-----------|------|
  | services/order/ | 订单主流程编排 | 独立 | 拆为 order 子模块 |
  | services/user/ | 用户资料读写 | 独立 | 拆为 user 子模块 |
  | services/utils/ | 通用工具函数 | 合并 | 保留为本模块内部结构 |
- **审计结论**：由单模块升级为 Group / 保持单模块 / 部分拆分
- **豁免声明**（若适用）：见 1.6.5
```

#### 1.6.5 豁免规则（谨慎使用）

以下情况允许**不下钻**，但必须在「## 备注」显式声明豁免依据：

| 豁免场景 | 依据说明 |
|---------|---------|
| **技术分层内聚** | 二级子目录是同一业务域的技术分层（controller/service/dao），符合 1.4「分层架构合并模块」— 应合并为单模块 |
| **DTO/Model 集合** | 二级子目录是纯数据结构定义（如 `models/`、`dto/`、`types/`），无独立行为 |
| **迁移过渡态** | 目录内是历史遗留的旧版本代码，即将删除，无维护价值 |
| **框架强制目录** | 二级子目录是框架强制生成的（如 Django `migrations/`、Vue `.nuxt/`），非人为组织 |

> ⚠️ 豁免场景之外的所有情况都必须走 1.6.2 抽样验证，不得基于"我看着像单模块"直接跳过。

### 1.4 大模块（Group）识别与分组决策（v1.9 新增）

> 目的：当项目模块数量较多时，将"高内聚的一组子模块"聚合为一个 Group 目录，帮助 Agent 三级下钻按需加载，节省 token。

**分组判定条件**（满足全部 3 条才建 Group 目录）：

| 判定项 | 通过条件 | 反例 |
|-------|---------|------|
| **内聚性** | 该组内的子模块协同解决**同一个大问题域**（如「用户体系」「订单系统」「Agent Runtime」） | 只是恰好在同一目录，职责毫无关联 |
| **数量阈值** | `SUB_MODULE_COUNT ≥ 3`（含 3） | 只有 1~2 个子模块，无需嵌套目录，直接放在 `modules/` 顶层 |
| **对外收敛** | 组内子模块对外调用主要通过少数几个入口子模块暴露，其他子模块基本只被组内引用 | 每个子模块都是对外入口，本质是并列关系而非层级 |

**分组决策流程**：

```
候选模块清单（Step 1.1~1.3 产出）
   ↓
对每对高内聚候选做 1.4 三条判定
   ↓
满足 → 建 Group 目录（modules/<group>/）
   ↓
为该 Group 生成 group.md（用 templates/module-group-template.md）
   ↓
将子模块档案放到 modules/<group>/<sub-module>.md
   ↓
不满足 → 顶层单模块（modules/<module>.md）
```

**层级深度约束**（v1.9 硬性）：

- **只支持 2 层**：`modules/<group>/<module>.md`，**禁止**再往下嵌套 `modules/<group>/<subgroup>/<module>.md`
- 若真的存在 3 层结构诉求，用 `<group>/group.md` 内部的 Markdown 二级标题分块表达，不得用文件系统嵌套

**顶层单模块 vs Group 的选择**：

| 场景 | 处置 |
|-----|------|
| 独立单模块（如一个通用工具库） | `modules/<name>.md` |
| 只有 2 个协同子模块 | 各自 `modules/<name>.md`（顶层），不建 Group |
| 3 个及以上高内聚子模块 | `modules/<group>/group.md` + `modules/<group>/<sub>.md`\* |
| 分层架构下的同一业务域（controller/service/dao 三件套） | 合并为**单一模块**（不是 Group），归入 `modules/<domain>.md`

> 📌 关键区分：**Group** 是"多个独立子模块的容器"；**分层架构合并模块** 是"跨层的同一实体聚合成单模块"。二者不要混淆。

## Step 2 · 调用关系扫描规范

> 目标：为每个模块**完整识别**"上游依赖 / 下游调用方 / 下游数据调用" 三类关系，深度均为 **1 层**。

### 2.1 三类关系的定义（严格区分）

| 关系类型 | 方向 | 含义 | 举例 |
|---------|------|------|------|
| **上游依赖**（Upstream） | 本模块 → 外部 | 本模块 `import` / `require` / `use` 了哪些外部模块 | `payment` 模块 import 了 `user` 模块的 `getUserById` |
| **下游调用方**（Downstream Callers） | 外部 → 本模块 | 谁 `import` 了本模块、调用了本模块的对外接口 | `order` 模块调用了 `payment.pay()` |
| **下游数据/接口调用**（Downstream Data Calls） | 本模块 → 外部资源 | 本模块调用的**外部资源**：数据库表、外部 HTTP API、消息队列、缓存、第三方 SDK | 本模块查询了 `t_user` 表、调用了 `https://api.xxx.com/v1/foo`、`redis GET user:*` |

> **关键区分**：
> - "上游依赖" 指**代码级模块间**依赖
> - "下游数据调用" 指**跨系统/资源边界**的调用（不是本仓库内的其他模块）
> - "下游调用方" 是被谁用（反向查询）

### 2.2 扫描技术手段（Agent 执行时的推荐方式）

#### A. 上游依赖扫描（正向）

```
对模块内所有源文件执行：
  1. 提取所有 import / require / use / include / #include 语句
  2. 过滤掉标准库、第三方库（保留仓库内其他模块的引用）
  3. 按被引模块聚合，去重
```

#### B. 下游调用方扫描（反向）— 关键强化点

```
对本模块的每个对外接口/公共导出符号：
  1. 用 grep_search / codebase_search 全仓库搜索该符号的使用位置
  2. 排除模块自身内部的引用
  3. 按引用方所在模块聚合
  4. 记录：调用方模块名 + 使用了哪个接口 + 大致次数
```

**Agent 执行提示**：
- 优先用 `grep_search`（精确符号名）搜索导出符号
- 对通用名（如 `get`、`create`）需结合命名空间/包名限定，避免误匹配
- 若命中数 > 100，只保留 Top 10 调用方模块，末尾注明 `（另有 N 处调用，未逐一列出）`

#### C. 下游数据调用扫描

```
在模块源码中搜索以下模式，识别外部资源调用：
  - SQL：SELECT / INSERT / UPDATE / DELETE 语句中的表名
  - HTTP：http.Get/Post、fetch、axios、requests、reqwest 等 URL
  - Redis：redis.Get/Set、rdb.HSet 等 key 模式
  - MQ：publish/subscribe/kafka.Produce 等 topic 名
  - 第三方 SDK：明确标识的外部服务调用
```

### 2.3 扫描输出规范

三类关系分别写入模块档案的独立章节（详见模板变更）：

```markdown
## 上游依赖（我依赖谁）
- <模块A>：使用其 xxx 接口做 xxx
- <模块B>：使用其 xxx 数据结构

## 下游调用方（谁依赖我） · 1 层直接调用
- <模块X>：调用本模块的 `pay()`、`refund()`
- <模块Y>：调用本模块的 `getPaymentStatus()`
（另有 N 处调用未逐一列出）

## 下游数据/接口调用（我调用的外部资源） · 1 层
- 数据库表：`t_payment`（读写）、`t_user`（只读）
- 外部 HTTP：`POST /api/v1/notify`（回调通知服务）
- Redis Key：`payment:lock:{orderId}`（分布式锁）
- 消息队列：`topic:payment.result`（发布支付结果）
```

## Step 3 · 首次台账建立流程（v1.9 分层版本）

> 前提：项目从未建立过模块台账，或用户显式要求全量重建。

```
1. 复用 09-module-analysis.md 的工程结构识别（Step 2）
   ↓
2. 应用本工作流 Step 1.1~1.3 的粒度标准，生成**扁平候选模块清单**
   ↓
2.5. **【v1.10 新增，硬性】** 应用 Step 1.6 的递归下钻硬标准：
     2.5.1 对每个候选模块检查 T1~T4 触发条件
     2.5.2 触发任一 → 执行 1.6.2 子域抽样验证，修订候选清单
     2.5.3 每一次下钻决策必须在拟建档模块的「## 备注 · 下钻审计记录」留痕
     2.5.4 迭代直到候选清单中不再有触发下钻的胖候选
   ↓
3. 应用 Step 1.4 的分组决策，识别大模块（Group）：
   3.1 对下钻后修订的候选模块做高内聚聚类，得到 Group 划分方案
   3.2 满足分组判定条件（3 条）的组 → 建 Group 目录 modules/<group>/
   3.3 未归入任何 Group 的模块 → 保留为顶层单模块 modules/<module>.md
   ↓
4. 对每个大模块 Group：
   4.1 用 templates/module-group-template.md 生成 modules/<group>/group.md
   4.2 填写 group.md 的「Group 概览」「内部结构关系图」「Group 级对外接口」
   4.3 填充头部 LAST_ANALYZED = 今日日期，SUB_MODULE_COUNT = N
   ↓
5. 对每个（Group 内 or 顶层）模块：
   5.1 应用 Step 2 扫描三类关系
   5.2 用 templates/module-template.md 生成模块档案
   5.3 填充头部 MODULE_GROUP（属于哪个 Group，顶层单模块填 -）
   5.4 填充头部 INVOLVED_CHAINS = -（首次建档时无涉及链路，由 16 号推导时反向填入）
   5.5 填充头部 LAST_ANALYZED = 今日日期
   5.6 **【v1.10 新增】** 将 Step 2.5 的下钻审计记录固化到「## 备注」章节
   ↓
6. 回填 group.md 的「子模块清单」表
   ↓
7. 汇总所有 Group + 顶层单模块，更新顶层 modules/index.md（v1.9 只列 Group + 顶层单模块，不列子模块）
   ↓
8. 向用户输出台账建设报告（详见 Step 7 输出格式，v1.10 报告新增下钻审计统计）
```

## Step 4 · Agent 使用台账的标准协议

> 每次接到**代码修改类任务**时，Agent 必须按以下顺序执行，禁止跳过。

```
[任务开始]
   ↓
① 读取 modules/index.md
   ↓
② 用任务描述关键词匹配"关键词"列，命中候选模块列表
   ↓
③ 对命中模块执行【时效性校验】（Step 6）
     ├─ 全部有效 → 加载对应模块档案
     └─ 有过期项 → 先执行【增量更新】（Step 5），再加载
   ↓
④ 基于加载的模块档案，规划改动范围：
     - 主改动模块：修改点所在模块
     - 影响面模块：主改动模块的"下游调用方"（可能被波及）
     - 依赖检查：主改动模块的"上游依赖"（是否需要联动改）
   ↓
⑤ 执行代码修改
   ↓
⑥ 【任务完成前强制】对所有被改动的模块执行【增量更新】（Step 5）
   ↓
⑦ 向用户报告任务完成 + 台账已同步
```

> ⚠️ 未执行 ⑥ 就报告任务完成，视为**流程违规**。

## Step 5 · 增量更新流程（自动 + 手动共用）

### 5.1 触发条件

| 触发方 | 场景 |
|-------|------|
| Agent 自动 | 代码修改任务完成时（强制） |
| Agent 自动 | 检测到模块档案时效性过期时（强制） |
| 用户手动 | 显式指令："更新 xxx 模块台账" |

### 5.2 更新步骤

```
1. 识别本次涉及的文件列表（git diff / 修改记录 / 用户指定）
   ↓
2. 通过 modules/index.md 的"文件链接"或反查文件路径，
   映射到受影响的模块列表
   ↓
3. 对每个受影响模块：
   3.1 保留档案中的手动补充内容（## 备注、用户显式标记的段落）
   3.2 重新扫描三类关系（Step 2），差量更新对应章节
   3.3 更新档案头部 <!-- LAST_ANALYZED: YYYY-MM-DD -->
   3.4 **【v1.10 新增，硬性】** 复检 Step 1.6 的下钻触发条件：
         - 若触发 T1/T2/T4/T5 → 必须执行子域抽样并追加「## 备注 · 下钻审计记录」
         - 若触发 T3（一句话职责含并列词）→ 视为**边界劣化**，强制拆分/建 Group
         - 抽样结论若产出新的子模块 → 走 Step 3 的 4~7 建档流程
   ↓
4. 检查是否发生"模块边界变化"：
     - 新增了对外入口文件 → 检查是否需要新建模块
     - 删除了对外入口文件 → 检查是否需要合并/删除模块
     - 单模块规模超越 1.2 软阈值上限一倍 → 提示用户复核拆分
     - **【v1.10 新增】** 单模块档案 `.md` > 800 行 或 内部主题 ≥ 5 → 触发 1.6.3 反向审计
   ↓
5. 同步更新 modules/index.md：
     - 「最后更新」列 = 今日
     - 「时效状态」列 = 🟢 有效
     - 若有新增/删除模块 → 增删索引行
```

### 5.3 更新粒度

- **默认增量**：只重扫本次改动涉及的模块
- **级联触发**：若受影响模块的**对外接口签名发生变化**，则**自动级联**刷新其"下游调用方"列表中的模块档案（因为这些模块的"上游依赖"章节可能也变了）
- **级联深度**：仅 1 层级联，防止无限扩散

### 5.4 顺带聚合 MQ 反查表

每次执行 Step 5 增量更新时，**若受影响模块的「下游数据/接口调用」章节包含 MQ 发布/订阅**，需顺带更新 [`.agent-workflow/modules/_topics.md`](../modules/_topics.md)：

1. 从受影响模块档案提取 MQ 条目（`发布` / `订阅`）
2. 更新 `_topics.md` 的对应 topic 行（新增/删除发布方或订阅方）
3. 触发一致性检查（多发布方 / 孤儿 topic / 无发布方订阅），告警写入 `_topics.md` 的「一致性告警」段
4. 更新 `_topics.md` 的 `<!-- LAST_ANALYZED -->` 头

> 该反查表是 [16-call-chain-derivation.md](./16-call-chain-derivation.md) 的关键输入，缺失或过期会导致链路推导时 MQ 环节断链。

### 5.5 链路档案级联失效（v1.8 新增，硬性；v1.9 快照格式升级）

每次完成单个模块档案的刷新后（Step 5 中 3.3 完成 `LAST_ANALYZED` 更新），Agent **必须**执行链路档案联动失效：

1. 读取 `.agent-workflow/chains/index.md`，获取所有链路档案的 `SOURCE_MODULES_SNAPSHOT`
2. 对每条链路，若其 `SOURCE_MODULES_SNAPSHOT` 中包含本次更新的模块（**v1.9 匹配规则**：按 `<group>/<module>` 或 `<module>` 完整路径匹配，避免 Group 内同名子模块误伤）→：
   - 将链路档案的 `STATUS` 置为 `STALE`（若当前不是 `ABANDONED`）
   - 将 `chains/index.md` 对应行的「时效」列置为 🔴，「状态」列同步为 🔴 STALE
   - 在链路档案的「变更历史」追加一行：`| YYYY-MM-DD | 联动置为 STALE | <group>/<模块名> 模块 LAST_ANALYZED 由 X 更新为 Y |`
3. 只降级不重推：15 **不会**自动触发链路重推（避免为一次改动消耗大量 tokens）；重推由用户显式触发 `刷新调用链档案 <slug>`
4. 若 `chains/` 目录不存在或未推导过任何链路，本步骤静默跳过，不报错

### 5.6 双向反向索引维护（v1.9 新增，硬性）

> 目的：让**模块档案 ↔ 链路档案**互相可导航，Agent 从任一端出发都能快速定位另一端。

模块档案的头部 `INVOLVED_CHAINS` 是链路档案的**反向索引**，规则如下：

| 事件 | 联动动作 |
|-----|---------|
| 新增或刷新单个模块档案（Step 5 之内） | **不主动重扫全部链路**；`INVOLVED_CHAINS` 由 16 号 Step 6.7 落档时反向注入维护，本步骤不处理 |
| 模块档案迁移路径（如从 `payment.md` 移到 `pay/gateway.md`） | 扫全部链路档案，把 `SOURCE_MODULES_SNAPSHOT` 中的旧路径替换为新路径；同时更新链路档案「变更历史」追加一行 `| YYYY-MM-DD | 模块路径变更 | payment → pay/gateway |` |
| 模块档案删除（不再使用） | 扫全部链路档案，若涉及该模块 → 将该链路 STATUS 置为 STALE 并追加变更历史 |

> 📌 反向索引 `INVOLVED_CHAINS` 的**维护方**是 16 号 Step 6.7（落档时注入），**消费方**是 Agent 加载模块档案时读取。15 只在**模块迁移/删除**时对全量链路做兜底扫描，日常刷新不做扫描避免开销。

### 5.7 Group 索引联动更新（v1.9 新增，硬性）

对属于某个 Group 的子模块做增量更新时，还必须联动更新其 `<group>/group.md`：

1. 若子模块**新增/删除** → 更新 `group.md`「子模块清单」表 + 头部 `SUB_MODULE_COUNT` 字段
2. 若子模块的**职责概述**发生变化 → 同步更新 `group.md` 表中对应行的「一句话职责」列
3. 若子模块的**关键词**发生变化 → 同步更新 `group.md` 表中对应行的「关键词」列
4. 若子模块的**LAST_ANALYZED** 或**状态**发生变化 → 同步更新 `group.md` 表中对应行的「最后更新」和「时效」列
5. `group.md` 的头部 `LAST_ANALYZED` 更新为今日

> ⚠️ 顶层单模块（`MODULE_GROUP: -`）不涉及本步骤。

> ⚠️ **硬性约束**：15 Step 5 刷新完成后汇报前必须完成 5.5 联动，未完成视为任务未完成。

> 💡 链路档案与本台账的联动详见 [16-call-chain-derivation.md Step 6-7](./16-call-chain-derivation.md#step-6--落档规范v18-新增硬性)。

## Step 6 · 时效性校验规则

### 6.1 时效状态定义

在 `modules/index.md`（顶层索引）与 `modules/<group>/group.md`（Group 索引）表格中都需要维护「时效状态」列：

| 状态 | 含义 | 判定条件 |
|-----|------|---------|
| 🟢 有效 | 档案与代码一致 | `LAST_ANALYZED` 之后，模块相关文件**没有** git 变更 |
| 🟡 待验证 | 可能过期 | `LAST_ANALYZED` 之后模块内文件有过 commit，但 Agent 尚未复核 |
| 🔴 已过期 | 明确过期 | 模块入口文件、对外接口文件被修改后未刷新台账 |
| ⚪ 未建档 | 目录存在但未分析 | 首次全量扫描后新增的目录 |

### 6.2 校验时机

| 时机 | 校验强度 |
|------|---------|
| Agent 加载模块档案前 | **强制**：🔴 必须先刷新，🟡 建议先刷新（视任务重要性），🟢 可直接用 |
| 用户执行"体检模块台账"指令时 | 全量校验并输出报告 |

### 6.3 判定实现（推荐）

Agent 通过下列方式判定时效状态（择一或组合）：

- 对比 `LAST_ANALYZED` 日期与模块内文件的 `git log` 最新 commit 时间
- 若无法访问 git，则默认将 `LAST_ANALYZED` 超过 30 天的档案标为 🟡
