# Agent 工作流使用指南

> 本文件包含工作流模板的使用说明。入口索引文件：[AGENTS.md](../AGENTS.md)

---

## 工作流生命周期三阶段

本工作流分为三个阶段，**阶段三依赖阶段一完成**：

| 阶段 | 名称 | 前置条件 | 说明 |
|:----:|------|---------|------|
| **一** | 📐 项目工作流分析 | 无 | 首次接入必须完成，完善度 ≥ 80 分且用户宣告后解锁阶段三 |
| **二** | 📦 业务模块分析 | 无（独立） | 任何时候均可进行，不阻塞也不被阻塞 |
| **三** | 🛠️ 开发维护任务 | **阶段一必须完成** | 创建任务前 Agent 自动检查阶段一状态 |

> 💡 当前阶段状态存储在 `AGENTS.md` 顶部的 `LIFECYCLE_PHASE` 元数据中，Agent 每次启动时自动读取。

## 前置条件

- 工作区中已存在模板文件（`AGENTS.md` + `.agent-workflow/` 目录）
- 使用任意支持对话的 AI Agent（如 Cursor、Windsurf、CodeBuddy、Copilot Chat 等）
- （可选）如需使用 Git 平台的分支/PR 功能，确保 Agent 具备相应的 Git 平台操作能力

## 自动分析（推荐）

在 Agent 对话中输入以下指令，触发自动分析（Agent 将参考 [analyzer-instructions.md](./analyzer-instructions.md) 执行分析）：

**整体分析** — 一次性扫描并填充所有模块：
```
分析项目工作流
```
或
```
请帮我分析当前项目的开发工作流，填充所有模块文档
```

**单模块分析** — 只分析指定模块：
```
分析编译流程
分析测试流程
分析分支提交规范
```

**重新分析** — 对已完成的模块重新分析（会覆盖自动生成的内容，保留手动补充的部分）：
```
重新分析编译流程模块
```

**模块台账与调用链推导**— 基于 15/16 两个治理层元流程，在阶段二之上提供持续维护与链路推导能力：
```
建立模块台账              # 首次建库（等价 15 Step 1-5 全量刷新）
刷新模块台账              # 周期性体检并修正时效性
更新 user-auth 模块台账   # 局部刷新单个模块
检查模块台账时效性       # 仅扫描不修改，输出🟢/🟡/🔴分布
画出 /login 的调用链    # 16 入口→落库全链路推导（v1.8 默认落档到 chains/）
列出已推导的调用链        # v1.8 新增：展示 chains/index.md 档案清单
刷新调用链档案 <slug>    # v1.8 新增：重推并覆盖旧档案
确认调用链 <slug>          # v1.8 新增：STATUS DERIVED → VERIFIED
作废调用链 <slug>          # v1.8 新增：STATUS → ABANDONED
分析 UserSvc.Login 的影响面 # 16 反向影响面分析
谁写入了 t_user_login       # 16 数据反查（表/topic/接口）
```

> 💡 15 不仅是命令驱动，更重要的是它通过 03 Step 3.1 / Step 10.1 / 11 提交前置三个硬门禁自动驱动（详见下文「模块台账与调用链推导」章节）；16 则是纯按需读取，不干预主流程。

## 手动填写

直接编辑 `workflows/` 下的对应流程文件，填写内容区域（`<!-- CONTENT_START -->` 和 `<!-- CONTENT_END -->` 之间），完成后手动更新文件头部的状态标记：

```markdown
<!-- STATUS: DONE -->
<!-- LAST_ANALYZED: 2026-04-09 -->
```

同时需要同步更新以下两处：

1. **`AGENTS.md` 工作流程状态总览表**：修改对应行的状态列（🔴 → 🟢/🟡）和「最后更新」列
2. **`AGENTS.md`「🔰 当前阶段状态」面板**：重新计算完善度得分并更新「完善度得分」行

> 💡 也可以直接输入 `查看工作流完善度`，让 Agent 自动重新计算并更新面板。

## 模板复用到新项目

将以下文件/目录复制到目标项目根目录即可：

```bash
cp AGENTS.md /path/to/new-project/
cp -r .agent-workflow/ /path/to/new-project/
```

> 💡 复制后所有模块状态会重置为"待实现"，在新项目中重新运行分析即可。

## 元数据字段含义

模板中存在多处时间/版本字段，含义不同，注意区分：

| 字段 | 出现位置 | 维护方式 | 含义 |
|------|---------|---------|------|
| `WORKFLOW_VERSION` | `AGENTS.md` | 手动 | 模板整体契约版本 |
| `ANALYZER_VERSION` | 每个 `workflows/*.md` 文件头 | 手动 | 该工作流兼容的分析器版本，需与 `WORKFLOW_VERSION` 配套 |
| `LAST_UPDATED` | `AGENTS.md` | 手动 | 入口索引文件最后一次人工修改的日期 |
| `LAST_ANALYZED` | 每个 `workflows/*.md` 文件头 | 自动 | 该工作流最近一次被 Agent 自动分析的日期 |
| `STATUS` | 每个 `workflows/*.md` 文件头 | 自动+手动 | 流程文档完成度：TODO / PARTIAL / DONE |

## 自定义扩展

如需添加新的工作流模块：

1. 复制 `templates/workflow-template.md` 到 `workflows/` 目录
2. 按编号规则重命名（如 `17-your-workflow.md`，注意 14/15/16 已被占用：14 自检 / 15 模块台账 / 16 调用链推导）
3. 填写流程标题和结构化内容区域
4. 在 `AGENTS.md` 状态总览表中添加对应行
5. （可选）在 `analyzer-instructions.md` 中添加对应的检测规则

如需添加新的业务模块文档：

1. 复制 `templates/module-template.md` 到 `modules/` 目录
2. 按业务模块名称命名（如 `user-auth.md`）
3. 填写模块信息

## 工作流自检（治理）

`.agent-workflow/` 是用文档承载的 SOP 体系，**文档质量本身也需要持续治理**。模板内置了一个**元流程**——`workflows/14-workflow-self-check.md`，用于审计 01-13 与任务 SOP 的质量。

### 适用场景

- ✅ 阶段一完成后，定期巡检 SOP 是否仍闭环、是否有歧义
- ✅ 接手他人维护的 `.agent-workflow/` 后，先做一次体检再上手
- ✅ 修订过某个流程文档后，确认对其他流程的引用是否同步
- ❌ **不**作为代码 PR 的合入门禁（避免治理悖论）

### 与阶段一完善度的区别

| | 阶段一完善度 | 工作流自检 |
|---|---|---|
| **关注点** | 有没有写（STATUS） | 写得好不好（正文质量） |
| **触发频率** | 一次性，解锁阶段三 | 周期性 / 按需 |
| **产出** | 0/100 完善度分 | 0/100 健康度分 + 缺陷清单 |
| **是否影响阶段三** | 是（≥80 分才解锁） | 否（仅治理参考） |

### 常用指令

```
启动工作流自检       # 全量体检（13 流程 + 任务 SOP + 关键流闭环）
自检 编译流程        # 单流程体检
自检 关键流          # 仅查"需求 → 分支 → 编译 → 测试 → 提交 → PR → CI → 归档"闭环
查看自检报告         # 复读上次结果（缓存于 .audit-cache.md）
忽略缺陷 #N         # 把第 N 条缺陷写入 audit-baseline.md，后续不再报告
```

### 7 大检查维度速览

| 维度 | 关注点 |
|------|-------|
| D1 完整性 | 占位符是否替换、必填章节是否齐全 |
| D2 歧义性 | 有无含糊词、命令是否给出确切字符串 |
| D3 可执行性 | 命令能否直接 copy-paste 运行 |
| D4 闭环性 | 关键流的每一跳是否有显式衔接 |
| D5 一致性 | 跨文件引用是否互相矛盾 |
| D6 可验证性 | 是否有验收 / 通过条件 |
| D7 可恢复性 | 是否有回滚 / 阻塞解除路径 |

> 📖 详细规则、报告格式、健康度算法见 [`workflows/14-workflow-self-check.md`](./workflows/14-workflow-self-check.md)。

## 模块台账与调用链推导（治理）

除 14 自检外，模板还内置两个面向 Agent 长期记忆的元流程——**15 模块台账**（维护）与 **16 调用链推导**（消费），目的是把 Agent 临时扫代码的短期认知固化为项目的长期索引，避免每次改代码都重复扫描、重复花 tokens。

### 三层面的分工

| 层 | 流程 | 职能 | 触发时机 |
|:---:|------|------|---------|
| 分析 | 09 模块分析 | 首次全量扫描，生成 `modules/*.md` | 阶段二，手动触发 |
| 维护 | **15 模块台账** | 局部刷新 + 时效追踪 + 反向扫描 | 03/11 硬挂钩 + 手动 |
| 消费 | **16 调用链推导** | 入口→落库链路 / 影响面 / 数据反查 | 按需手动 |

### 15 的三个硬门禁（重点）

15 不仅是命令驱动，它通过以下三个挂钩点**强制**与主流程同频：

1. **03 Step 3.1 查台账**：任务进入实现前，Agent 必须先 grep `modules/index.md` 定位相关模块卡片，避免盲改
2. **03 Step 10.1 刷台账**：提交前，Agent 必须根据 diff 受影响范围刷新 `modules/<name>.md` + `_topics.md`（如有新增/删除 topic）
3. **11 提交前置门禁**：`git commit` 前必须确认台账已同步且 `FRESHNESS_STATUS` 全部 🟢，否则阻断提交

### 时效状态机

每份 `modules/<name>.md` 头部携带 `FRESHNESS_STATUS` 字段：

| 状态 | 含义 | 产生时机 |
|:---:|------|---------|
| 🟢 Fresh | 台账与代码一致 | 刚刚刷新完成 |
| 🟡 Stale | 代码变了台账未刷新 | 15 反向扫描发现 diff |
| 🔴 Missing | 模块未建立档案或代码已删除 | 15 Step 4 检测到 |

### 16 v1.7 分叉表达能力

调用链推导实际使用中，同一入口经常会**从单链分叉成多链**——条件路由、扇出并发、MQ 一发多订、interface 多实现、内存事件总线等。v1.7 为 16 号工作流补齐了分叉表达能力：

| 分叉类型 | 语义 | 图形约定 |
|---------|------|---------|
| **conditional** | 运行时二选一/多选一（if/switch/策略） | mermaid `alt/else` + 条件表达式 |
| **sync fan-out** | 同步并发多下游，任一失败 → 主链失败 | 实线箭头 + `sync:` 前缀 |
| **async fan-out** | 异步扇出（MQ/EventBus/协程），失败降级 | 虚线箭头 + `async:` 前缀 |
| **polymorphic** | interface 有多实现，静态无法确定运行时走哪条 | `possible:` 前缀 + `Note over X: ⚠️ 多态分叉` |
| **event-bus** | 内存事件总线（非 MQ）触发多 handler | 与 async fan-out 同规范 + 事件总线断点 Note |

**成环剪枝**（v1.7 硬性要求）：BFS 展开时若 `current ∈ path` → 画 `cycle-back` 边并 ⚠️ 标注，终止该分支，避免无限展开。

档案侧配合：在 `modules/<name>.md`「上游依赖」段用 `conditional / sync fan-out / async fan-out / polymorphic / event-bus` 标注分叉类型，16 推导时可直接读档案生成分叉图，无需二次扫代码。

### 常用指令

```
建立模块台账                    # 首次建库（等价全量刷新）
刷新模块台账                    # 周期性体检 + 修正 Stale/Missing
更新 <name> 模块台账            # 局部刷新单个模块
检查模块台账时效性             # 只扫不改，输出🟢/🟡/🔴分布报告
刷新 topic 反查表                # 重建 `modules/_topics.md`

画出 <入口> 的调用链            # 16 正向推导（入口 → 落库）
分析 <模块.接口> 的影响面     # 16 反向影响面（改它会影响谁）
谁写入了 <表名/topic>            # 16 数据资源反查
```

> 💡 15 与 09 共存不矛盾：09 负责首次全量，15 负责后续维护，二者产物写入同一份 `modules/<name>.md`。
>
> 📖 详细规则见 [`workflows/15-module-inventory.md`](./workflows/15-module-inventory.md) 与 [`workflows/16-call-chain-derivation.md`](./workflows/16-call-chain-derivation.md)。

### 16 v1.8 链路落档与复用（新增）

从v1.8 开始，16 号推导的产物**默认落档**到 [`.agent-workflow/chains/`](./chains/) 目录，成为 Agent 跨会话的共享记忆。不再需要每次重新扫代码推导相同链路。

**链路档案生命周期**：

| 状态 | 图标 | 含义 | 产生时机 |
|:---:|:---:|------|---------|
| `DERIVED` | 🟡 | 首次推导完成，等待核对 | 16 Step 5 首次落档 |
| `VERIFIED` | 🟢 | 用户已核对确认 | 用户回复“确认”或触发 `确认调用链 <slug>` |
| `STALE` | 🔴 | 沿途模块档案已更新，链路可能失真 | 15 Step 5.5 联动触发 |
| `ABANDONED` | ⚫ | 业务下线 / 入口废弃 / 用户作废 | 用户触发 `作废调用链 <slug>` |

**关键行为**：

- **默认落档**：除非用户显式 `--no-persist`，每次推导都写入 `chains/<chain-type>-<entry-slug>.md`
- **命中复用**：下次接到同样入口 + 同类型的推导请求，直接加载旧档案（前提 STATUS ∈ {DERIVED, VERIFIED}），不重扫代码
- **只降级不重推**：15 Step 5.5 只将链路置为 `STALE`，不自动重推（避免为一次改动消耗大量 tokens）
- **人工担保升级**：Agent 不得自动将 `DERIVED` 升级为 `VERIFIED`，必须用户显式确认

> 💡 链路档案与模块台账的联动契约：链路档案头部的 `SOURCE_MODULES_SNAPSHOT` 字段快照了沿途模块推导时的 `LAST_ANALYZED`；15 刷新任一模块后会自动扫描 `chains/index.md` 失效相关链路。

### 15/16 v1.9 模块分层结构与三级下钻加载（新增）

从 v1.9 开始，`modules/` 支持**分层组织**，Agent 采用**三级下钻**按需加载，避免全量扫描浪费 token。

**目录结构**：

```
modules/
├── index.md                    # L1 入口：只列 Group + 顶层单模块
├── <group>/                    # 大模块 Group 目录（≥3 个高内聚子模块）
│   ├── group.md                # L2 入口：Group 索引 + 子模块清单
│   └── <sub-module>.md         # L3 目标：子模块档案
└── <top-module>.md             # 顶层单模块（无 Group）
```

**三级加载协议**：

```
L1 · 读 modules/index.md，按关键词命中 Group 或顶层单模块
   ↓
L2 · 命中 Group 后读 <group>/group.md，二级关键词命中子模块
   ↓
L3 · 加载具体模块档案（<group>/<sub>.md 或 <top>.md）
```

**建 Group 的 3 条判定**（15 Step 1.4）：内聚性（同一大问题域）+ 数量阈值（`SUB_MODULE_COUNT ≥ 3`）+ 对外收敛（少数入口子模块暴露）。三条都满足才建 Group，否则保留为顶层单模块。

**双向反向索引**：模块档案头部 `INVOLVED_CHAINS` 记录参与的链路（16 Step 6.7 反向注入）；链路档案头部 `SOURCE_MODULES_SNAPSHOT` 用 `<group>/<module>@<date>` 格式记录沿途模块。Agent 从任一端出发都能快速定位另一端。

**Token 收益**：需精确定位单个子模块时，只需读 index.md（≤20 行）+ group.md（≤30 行）+ 子模块档案（1 份），远小于扫全部 100+ 档案。

## 任务目录使用方法

[`tasks/`](./tasks/) 目录用于存放**任务引导文件**，为每一份具体研发任务提供一份独立的“作战地图 + 进度档案”，支持 Agent 中断后无损恢复。

**快速开始**：

```
创建任务: 在订单页增加一个导出 Excel 的按钮
```

Agent 会自动：
1. 识别任务类型（feature / bugfix / refactor）
2. 从 [`templates/`](./templates/) 目录选取对应模板
3. 在 `tasks/_active/` 下生成 `<YYYYMMDD-slug>.md`
4. 与你对齐需求理解与验收标准
5. 填充实施计划（Step List）后请求你确认
6. 逐步推进，每完成一步勾选 + 追加进度日志

**其他常用指令**：

| 指令 | 说明 |
|------|------|
| `查看进行中的任务` | 列出 `tasks/_active/` 下所有任务 |
| `继续任务` / `继续任务 <task-id>` | 从首个未勾选项恢复执行 |
| `归档任务 <task-id>` | 完成后移入 `_archive/<YYYY-MM>/` |
| `废弃任务 <task-id>` | 标记 ABANDONED 并归档 |

> 📖 详细说明见 [`tasks/tasks-guide.md`](./tasks/tasks-guide.md)，完整 SOP 见 [`AGENTS.md`](../AGENTS.md) 的「📋 任务执行 SOP」章节。
